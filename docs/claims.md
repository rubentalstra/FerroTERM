# Claim evidence

Every factual claim FerroTERM makes in public, with the evidence behind it.
The public surfaces are `README.md`, the landing page (`website/landing/`),
and the book (`website/book/src/`). A claim here is anything a reader can
test: a code system served, a FHIR version, an operation, a performance
figure, a footprint, a licence statement, a conformance result, a dependency
claim.

The rule this file exists to enforce: a claim carries a test, a committed
pass list, a benchmark record, a spec citation, or a workflow step that
produces it. Two documents agreeing is not evidence. A claim with nothing
behind it is listed at the end, under
[Claims with no evidence](#claims-with-no-evidence), and is reworded or
removed before the release is cut.

This pass was taken on 2026-09-05 against `06934a648` on `main`, release
0.0.11, with `scripts/checks/versions.sh`, `scripts/checks/bench-table.sh
check`, and `scripts/checks/code-systems.sh` all passing. 176 claims were
checked; 22 of them lack evidence or overstate what the evidence shows.

Test paths are repo-relative. A test named here is the test that asserts the
claim, not a test that merely touches the area.

- `website/book/src/integrate/fhir-api.md`: "Expansions are flat today; nested
  `contains` is the v0.0.11 milestone."

All five are implemented and tested: nested `contains`
(`crates/fhir-terminology/src/operations/expand.rs` `nest()`;
`app/ferroterm-server/tests/it/value_set.rs::expand_by_get_and_post_returns_the_value_set_with_its_expansion`),
persisted resources (`app/ferroterm-server/tests/it/persisted.rs`), batch
(`app/ferroterm-server/tests/it/batch.rs`), `$closure`
(`app/ferroterm-server/tests/it/closure.rs`), and the implicit concept maps
(`crates/fhir-terminology/tests/it/snomed_concept_map.rs`, 10 tests).

`README.md` carries the same defect in its "What is next" section, which lists
"metrics and request identifiers" under v0.1.0. Both are built and tested
(`app/ferroterm-server/src/metrics.rs`, `request_log.rs`;
`app/ferroterm-server/tests/it/metrics.rs`).

The literal phrase "are v0.0.11" in these lists reads as a version-guard
rewrite of a stale milestone number, so the sentences no longer parse as
English either.

<a id="s3"></a>**S3. "The server exposes the FHIR terminology API on R4B"**

<a id="s4"></a>**S4. "a construct the artifact cannot answer (a description
module or effective time filter, a filter on inactive members) is

### Claims whose evidence is weaker than the claim

<a id="o1"></a>**O1. "Every failure is an `OperationOutcome` with a
`tx-issue-type` coding"** (`README.md`) and **"Every failure is an
`OperationOutcome` whose issue carries `severity`, `code`, `details.text`, and
a `details.coding` from ... `tx-issue-type`"**
(`website/book/src/integrate/fhir-api.md`). Every failure is an
`OperationOutcome`, and that part holds. The `details.coding` is emitted only
when a `Failure` carries a kind (`app/ferroterm-server/src/outcome.rs:62-80`),
which 3 of the 55 `Failure::new` sites in the server crate set. Failures raised
by the terminology engine carry the coding; wire-layer refusals (a bad `mode`,
a bad FHIR id, `If-Match` 412, 410 gone, an unsupported search parameter, 415,
406, the closure 404 and 422, the fallback 404) do not. The tests say so both
ways:
`app/ferroterm-server/tests/it/ecosystem.rs::every_issue_and_outcome_carries_the_ecosystems_message_id`
asserts the coding on an engine failure, while
`tests/it/health.rs::unknown_route_is_an_operation_outcome` and
`tests/it/scope.rs::a_tx_resource_of_another_type_is_refused` assert only
`issue[0].code`.

<a id="o2"></a>**O2. "CycloneDX SBOMs"** (`README.md`, the Supply chain bullet,
in a sentence that also names the container image). The two binary SBOMs are
CycloneDX (`release-build.yml:129,151`, `cargo cyclonedx --format json
--spec-version 1.5`). The per-platform image SBOMs are SPDX
(`release-image.yml:186-194`, `syft scan -o spdx-json`, verified as
`--predicate-type https://spdx.dev/Document/v2.3`). The book's verifying page
is accurate: it names CycloneDX only for the binaries and says "the same
provenance and SBOM attestations" for the image.

<a id="o3"></a>**O3. "one static binary"** (`README.md`,
`website/landing/index.html`, `website/book/src/evaluate/comparison.md`,
`website/book/src/operate/install.md`). Two points. Only the two musl targets
are static; `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` link
dynamically against glibc, which `release-image.yml:72` states in its own
comment. And each tarball holds two binaries, `ferroterm` and `ferroterm-build`
(`release-build.yml:109`), which the install page says correctly a few lines
later.

<a id="o4"></a>**O4. "Every code system builds into the same four files"**
(`website/book/src/evaluate/architecture.md`, and the same four names in
`website/book/src/operate/configuration.md` and `loading-snomed.md`). RxNorm
writes no `hierarchy.bin` (`tools/ferroterm-build/src/rxnorm.rs:32,525-529`),
and SNOMED CT writes four files the page does not mention: `refsets.bin`,
`attributes.bin`, `members.bin`, and `identifiers.bin`
(`tools/ferroterm-build/src/pipeline.rs:48-54,257-260`, asserted by
`tools/ferroterm-build/tests/it/pipeline.rs::the_reference_set_memberships_are_written_beside_the_store`
and `::the_attribute_graph_member_tables_and_identifiers_are_written_beside_the_store`).
The page does list the RxNorm and ICD-11 extra files, so the gap is the SNOMED
ones and the RxNorm exception.

<a id="o5"></a>**O5. "the generic `concept is-a`, `descendent-of`, `is-not-a`,
`generalizes`, `in`, `not-in`, `regex`, and `exists` over any system with a
hierarchy"** (`website/book/src/integrate/fhir-api.md`), read against the same
page's rule that "the filters a system answers are the ones its provider
declares in `TerminologyCapabilities`". SNOMED CT declares only `concept` with
`is-a`, `descendent-of`, and `in`, plus `constraint` and `expressions`
(`crates/fhir-terminology/src/snomed.rs`, `filter_definitions`). The generic
operators do execute against SNOMED through the fall-through path in
`crates/fhir-terminology/src/filter.rs`, but they are undeclared, and they are
tested only against the fixture provider
(`crates/fhir-terminology/tests/it/filter.rs`). `concept is-a` is never
evaluated against the SNOMED provider in any test; only the shape of the
implicit `isa` filter is asserted.

<a id="o6"></a>**O6. "every operator, the description, concept, and member
filters, the history supplements, and alternate identifiers evaluate"**
(`website/book/src/integrate/ecl-value-sets.md`). The coverage is broad and
tested (`crates/fhir-terminology/tests/it/ecl.rs`, 11 tests spanning the
hierarchy operators, `^` with its field and nested forms, refinements with
cardinality, role groups, reverse and dotted attributes, `AND`, `OR`, `MINUS`,
all five filter families, and the history supplements). Three constructs are
refused with `EvalError::Unsupported` in `crates/sct-ecl/src/eval.rs`: a member
filter on `active = false`, a description `moduleId` filter, and a description
`effectiveTime` filter. A fourth, an acceptability concept other than
`PREFERRED` or `ACCEPTABLE` in a dialect filter, is refused and has no test, as
does the description `effectiveTime` refusal. The same page names the first
three refusals two paragraphs later, so the word "every" is the overstatement.

### Code systems with no test behind them

<a id="e2"></a>**E2. ICD-10 (WHO), `http://hl7.org/fhir/sid/icd-10`.** Served

uses the WHO URI: every ClaML test uses `http://hl7.org/fhir/sid/icd-10-nl`
(`tools/ferroterm-testkit/src/classification.rs:12`). The URI appears in the
repository only in a doc comment.

<a id="e3"></a>**E3. ICPC-2, `http://hl7.org/fhir/sid/icpc-2`.** No test, and
the URI appears in no Rust source. The claim rests entirely on the generic
ClaML loader answering any system URI you pass it.

<a id="e4"></a>**E4. The DHD Verrichtingenthesaurus.** The row names both DHD
thesauri, but one system URI exists (`crates/dhd-thesaurus/src/lib.rs:23`) and
the fixture is a Diagnosethesaurus delivery
(`tools/ferroterm-testkit/src/dhd.rs:11`). The Verrichtingen variant is not
separately exercised.

<a id="e5"></a>**E5. The NHG ICPC-1 to SNOMED CT map.** No occurrence of `nhg`,
`icpc1`, or the ConceptMap URL in any Rust source, test, fixture, or script.
The repository holds only `data/nhg/.gitkeep`. The generic `ConceptMap`
directory mechanism that the row describes does exist and is tested
(`app/ferroterm-server/src/state.rs:903-951`;
`crates/fhir-terminology/tests/it/concept_map.rs::the_store_loads_both_maps_with_the_r5_shapes_reduced`),
including the `"experimental": "false"` refusal the loading page documents, but
nothing substantiates this specific map. Of the twenty rows in the code systems
table, this is the only one with no evidence of its own at all.

<a id="e6"></a>**E6. The closure reinitialisation refusal.** The API page
documents `422` with `closure "[name]" must be reinitialized` when a code
system changes under a table. The branch exists
(`app/ferroterm-server/src/version/closure.rs:174-183`) and no test reaches it;
the only 422 closure test covers the unconfigured-database case.
