v0.1.0 released. Linux binaries and a container image, signed.

A pure-Rust FHIR terminology server for SNOMED CT, LOINC, ICD, RxNorm, and every FHIR code system, on ordinary hardware.

FerroTERM serves the HL7 FHIR terminology API on R4, R4B, R5, and the R6 ballot from one binary over an index built once per release and read at startup. No JVM, no search cluster. You bring the release you are licensed for; the build tool turns it into an index; the server answers from it.

What it serves

One seam, many code systems

Every code system reaches the FHIR operations through the same provider seam, so nothing in an operation is a special case for one system.

SNOMED CT, LOINC, UCUM, BCP 47, BCP 13, ISO 3166-1, ICD-10 (WHO), ICD-10-NL, ICD-10-CM, ICD-11 MMS, ICD-11 ICF, ICD-11 Foundation, ATC/DDD, ICPC-2, RxNorm, the DHD Diagnosethesaurus and Verrichtingenthesaurus, the G-Standaard, the Nederlandse Labcodeset, the NHG ICPC-1 to SNOMED CT map, and any FHIR CodeSystem, ValueSet, and ConceptMap resources. The code systems page lists each with its URI, versions, build command, and licence.

Four questions, four answers

Clinical informatics

What does it serve, and how well?

The code systems above, each from the release you license, with the inferred hierarchy, the preferred terms per language, and inactive concepts served and marked. Conformance is measured against the HL7 terminology ecosystem test suite per FHIR version, and the result is recorded, not claimed.

Operations

How do I run it, and what does it need?

One binary or a distroless container image, a directory of artifacts built once per release, and the memory the figures above show. Releases are built to SLSA Build Level 3 with signed provenance and SBOMs you verify before you run them.

Integration

How do I call it, from which FHIR version?

$lookup, $validate-code, $subsumes, $expand, and $translate under /r4, /r4b, /r5, and /r6, in JSON or XML, each version's parameter set generated from HL7's own packages so the surface is right by construction.
