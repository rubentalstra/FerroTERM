v0.0.8 released. Linux binaries and a container image, signed.

A pure-Rust FHIR terminology server for SNOMED CT, LOINC, ICD, RxNorm, and every FHIR code system, on ordinary hardware.

FerroTERM serves the HL7 FHIR terminology API from one static binary over a memory-mapped index built once per release. A Dutch SNOMED CT edition builds in 49 seconds into a 591 MB index, opens in half a second, and answers a lookup in a few milliseconds on a laptop, with no JVM and no search cluster to operate.

Why it exists

The same edition, on hardware you already have

SNOMED CT terminology servers today are almost all Java, and the reference server runs on Elasticsearch. That stack wants 16 to 32 GB of RAM to serve an edition, more than a laptop or a small box has.

Reference stack

16 to 32 GB

RAM to serve the International edition, most of it Elasticsearch heap, plus a search cluster to run.

FerroTERM, measured

591 MB on disk

The Dutch edition (548,949 concepts, 49 seconds to build) as one memory-mapped index, served by one Rust binary that started in half a second.

The data itself is small: a few hundred thousand concepts, a million descriptions, a million relationships. FerroTERM materializes the answers a terminology server is asked for once per release (the transitive closure as roaring bitmaps, the designations as a word index) and serves them from those structures. The figures above are measurements of the shipped build over a licensed edition on a laptop; the book records how they were taken.

What it serves

One seam, many code systems

Every code system reaches the FHIR operations through the same provider seam, so nothing in an operation is a special case for one system. You bring the release you are licensed for; the build tool turns it into an index.

SNOMED CT

Any RF2 edition: the inferred hierarchy as a transitive closure, preferred terms per language reference set, inactive concepts served and marked, the edition and version URI in every answer. ECL follows in v0.0.8.

LOINC, ICD-10, ICD-11, RxNorm

LOINC with its parts, answer lists, and linguistic variants; WHO ICD-10 and national translations from ClaML; ICD-10-CM; ICD-11 with postcoordination from the WHO local deployment; RxNorm with the FHIR relationship filters over typed edges.

Every FHIR CodeSystem, and the registries

A FHIR package or a directory of CodeSystem, ValueSet, and ConceptMap resources loads as is: HL7 Terminology's 900 systems, your own, and supplements. UCUM, BCP 47, BCP 13, and ISO 3166-1 ship inside the binary and need no configuration.

The FHIR terminology API

$lookup, $validate-code, $subsumes, $expand, and $translate on FHIR R4B, with request-scoped resources and $cache-control. The HL7 terminology ecosystem suite runs against every pull request; 120 of its 670 general cases pass today and the list only grows.

Machine-generated FHIR

The FHIR types and operation contracts are generated from HL7's own packages for R4, R4B, R5, and R6, so each version's surface is right by construction and a drift check keeps it that way. R4B is served now; the other three endpoints are the v0.0.9 milestone.

MIT licensed, verifiably built

The software is MIT. Releases are Linux binaries and a distroless image for amd64 and arm64, built to SLSA Build Level 3 with signed provenance and SBOMs you verify with gh attestation verify. The code systems are licensed by their owners and never distributed here.

Where the project is

v0.0.8 is the current release. It serves the code systems above on FHIR R4B and ships as signed Linux binaries, a container image, and a Compose file that builds an index from a release zip and serves it in two commands.

Next, in milestone order: the R4, R5, and R6 endpoints and XML (v0.0.9), and hierarchical expansion, persisted client resources, batch, and $closure (v0.0.10). The tracker's milestones are the roadmap; every issue carries its acceptance criteria.
